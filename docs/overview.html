One Action, Infinite Clouds

CloudMorph는 웹앱 소스를 넣거나 GitHub에 push하기만 하면, AI가 코드를 읽고 어디에 어떻게 띄울지 결정한 뒤 서버 Docker · Google Cloud Run · Cloud Run functions · 멀티 클라우드 VM 노드 풀에 배포하는 서비스입니다. 배포가 실패하면 오류 원문을 읽고 Dockerfile을 스스로 고쳐 다시 배포하고, DB가 필요하면 Postgres를 붙이며, 트래픽이 몰리면 다른 VM으로 번집니다.

지금 접속 주소. 서비스 자체가 GCP 서버 한 대(cloudmorph-control)에서 상시 돌고 있습니다. https://cloudmorph.34-64-253-41.sslip.io 로 누구의 노트북에서든 열 수 있고, API 토큰을 넣어야 배포할 수 있습니다. 노트북을 꺼도 서비스와 GitHub 웹훅은 계속 동작합니다.

수치는 10/10 실측입니다. 서울 리전(asia-northeast3), e2-small 노드 2대, 방명록(DB 포함) 앱 기준입니다.

ARCHITECTURE구조도와 시나리오 재생

구조도 아래에서 시나리오를 고르고 다음 또는 자동 재생을 누르면, 각 단계에서 어느 구성 요소가 일하는지 구조도에 강조됩니다. 아래 상자에는 그때 대시보드로 흘러가는 실제 이벤트 예시가 보입니다.

HOSTING어디서 돌아가나

처음에는 발표 노트북에서 서비스를 띄우고 터널로 공개했습니다. 이 방식은 노트북마다 gcloud 로그인, Docker, 키 파일을 다시 맞춰야 하고, 노트북을 끄면 웹훅도 멈춥니다. 그래서 서비스 자체를 GCP 서버 한 대에 올렸습니다. 같은 코드가 노트북에서도 그대로 돌기 때문에, 노트북 모드는 필요할 때만 쓰는 예비 수단으로 남겨 두었습니다.

소스는 어디로 가져오나

analyzer와 deployer는 백엔드가 돌고 있는 기계의 임시 폴더에서 일합니다. 지금은 그 기계가 서버이므로 다음과 같이 동작합니다.

· GitHub URL을 넣으면 서버가 직접 git clone해 임시 폴더에 받습니다. 가장 권장하는 입력입니다.
· 서버 경로(sample-apps/guestbook 등)는 서버에 있는 저장소 기준입니다. 내 노트북 폴더 경로는 서버에서 보이지 않습니다.
· ZIP은 서버에 올라와 있는 파일이어야 합니다. 브라우저에서 ZIP을 직접 올리는 기능은 아직 없습니다.

가져온 폴더는 타깃마다 따로 복사해 서로 섞이지 않게 하고, .env·키 파일은 복사 단계에서 뺍니다.

주소와 비용

주소 cloudmorph.34-64-253-41.sslip.io는 IP를 이름으로 바꿔 주는 무료 DNS(sslip.io)를 쓰고, 인증서는 Caddy가 Let's Encrypt에서 무료로 자동 발급합니다. 추가 비용이 없습니다.

"내 도메인"(예: cloudmorph.팀이름.com)을 쓰려면 도메인을 사야 합니다(연 1~2만 원). 그다음 Cloudflare 무료 계정에 도메인을 연결하고 서버 IP로 레코드 하나를 걸면 됩니다. 자동으로 되지는 않고 이 한 번의 설정이 필요합니다. 반면 로컬 타깃 앱에 붙는 *.trycloudflare.com 주소는 계정 없이 무료로 자동 발급되지만, 실행할 때마다 주소가 바뀝니다.

local 타깃의 의미가 바뀌었습니다. 서비스가 서버에서 돌면 local 타깃은 "서버 자신의 Docker"에 배포합니다. 회사 서버에 직접 올리는 온프레미스 배포와 같은 형태입니다. 내 노트북에 배포하는 장면이 필요하면 노트북에서 scripts/demo-up.sh로 같은 서비스를 띄우면 됩니다. 노트북은 공인 IP가 없어 서버가 노트북으로 들어갈 수 없기 때문입니다.

JOURNEY버튼 한 번의 여정

서버의 대시보드에서 One Action Deploy를 누른 순간부터 공개 URL이 뜰 때까지, 내부에서 일어나는 일을 순서대로 적었습니다. GitHub push로 시작될 때도 2단계부터는 같습니다.

1. 배포 요청

frontend

대시보드가 POST /deploy에 소스, 타깃 목록, 선택적으로 앱 이름과 브랜치를 보냅니다. 응답으로 받은 deployment_id로 즉시 SSE 스트림을 구독합니다.

2. 작업 생성과 잠금

main.py

작업 하나를 만들고 앱 이름(없으면 cloudmorph-<id>)을 정합니다. 같은 이름의 배포가 이미 돌고 있으면 queue: 로그를 남기고 끝날 때까지 기다립니다. 연속 push가 서로를 덮어쓰지 않게 하려는 장치입니다.

3. 소스 준비

main.py

서버 경로, ZIP, 허용된 GitHub URL 중 하나를 CloudMorph 서버의 임시 폴더로 가져옵니다. GitHub는 git clone --depth 1 --branch로 받고, .env나 키 파일 같은 비밀값은 복사 단계에서 제외합니다.

4. AI 분석

analyzer

Claude 검사관 17개가 읽기 전용 도구로 저장소를 직접 읽습니다. 언어, 프레임워크, 포트, 상태 저장 여부, 필요한 DB, localhost 바인딩 같은 위험을 찾고, 근거가 실제 파일에 없으면 버립니다. 결과로 권장 타깃, Dockerfile(없으면 AI가 작성), 판단 이유를 냅니다.

5. 타깃별 배포

deployer

타깃마다 작업 폴더를 따로 복사해 deploy(src_dir, dockerfile, target)를 호출합니다. 단계는 사전 점검 → 빌드 → 푸시 → 배포 → 공개 → 검증이고, 모든 외부 명령의 명령어·종료 코드·소요 시간을 기록합니다. 앱이 DATABASE_URL을 읽으면 Postgres도 이 단계에서 준비합니다.

6. 실패하면 자가치유

healer

deployer가 실패를 돌려주면 healer가 stderr를 분류하고 Dockerfile을 고쳐 다시 배포합니다. 최대 3회 반복하며, 결제 미연결처럼 코드로 고칠 수 없는 실패는 즉시 멈추고 사람에게 넘깁니다.

7. 공개 URL과 기록

main.py · frontend

성공하면 done 이벤트에 공개 URL이 실려 대시보드 카드에 뜹니다. 프로젝트 목록 파일에 상태와 URL이 저장되어 서버를 재시작해도 남습니다.

각 행이 무슨 뜻인가

성격. 앱이 어떤 종류의 기계 위에서 도는지입니다. local은 CloudMorph 서버 자신, cloudrun과 function은 구글이 관리하는 서버리스 환경, node는 우리가 빌린 VM입니다.

입력. 앞의 세 타깃은 analyzer가 고르거나 만든 Dockerfile로 이미지를 굽습니다. function은 구글의 빌드팩이 소스를 직접 읽기 때문에, 소스가 함수 모양이어야 합니다. Python은 @functions_framework.http가 붙은 함수, Node는 functions.http('이름', …)가 필요합니다.

빌드. Cloud Run은 x86(amd64) 서버만 쓰므로 이미지를 amd64로 만들어야 합니다. 서버가 x86이라 그대로 빌드됩니다. 노드 풀은 노드마다 아키텍처가 달라 노드에 맞춰 빌드합니다(예: 오라클 ARM VM이면 arm64).

이미지 전달. Cloud Run은 구글의 이미지 창고(Artifact Registry)에서 이미지를 당겨 갑니다. 노드 풀 VM에는 창고 인증을 두지 않고, 서버가 이미지를 SSH로 직접 흘려 넣습니다. 어느 회사 VM이든 인증 설정 없이 쓰기 위해서입니다.

공개 주소. 심사 기준인 "누구나 접근"을 위한 주소입니다. local은 cloudflared가 계정 없이 임시 주소를 발급하며 실행마다 바뀝니다. cloudrun과 function은 구글이 고정 HTTPS 주소를 줍니다. node는 라우터 VM의 고정 IP에 앱 이름을 붙인 주소입니다.

무중단 교체. 새 버전이 고장 나도 사용자가 깨진 화면을 보지 않게 하는 방법입니다. Cloud Run은 새 리비전을 트래픽 0%로 띄워 검증한 뒤에만 넘깁니다. 노드 풀은 라우터가 새 복제본이 응답할 때만 연결합니다.

DB와 자가치유. 아래 두 절에서 자세히 다룹니다. 함수는 매 요청마다 새로 떠도 되는 코드를 위한 것이라 DB를 붙이지 않고, Dockerfile이 없으니 Dockerfile을 고치는 자가치유도 적용되지 않습니다.

확장. cloudrun과 function은 요청이 몰리면 구글이 인스턴스를 늘리고, 없으면 0으로 줄입니다. node는 우리 감시 루프가 CPU를 보고 다른 VM에 복제합니다. local은 서버 한 대라 하나로 고정입니다.

첫 줄은 어느 단계에서 어떤 종류로 실패했는지, 둘째 줄은 진단 한 줄입니다. 진단은 컨테이너가 죽었는지, 5xx를 냈는지, 살아 있는데 엉뚱한 포트에서 듣는지를 구분합니다.

규칙이 먼저입니다. 데모 시나리오는 규칙만으로 고쳐져서 LLM API가 죽어도 동작합니다.

LLM은 붙어 있습니다. healer에는 LLM 폴백이 실제로 연결되어 있습니다. 규칙 표에 없는 오류(bad_entrypoint, unknown)이거나 규칙 패치가 듣지 않으면, healer가 stderr 끝부분과 현재 Dockerfile을 LLM에 보내 고친 Dockerfile 전체를 받아 다시 배포합니다. 순서는 Claude → OpenAI → 로컬 모델(vLLM·Ollama 등)이며, 키가 있는 첫 번째 것을 씁니다. 대시보드 패치 카드에 규칙 또는 LLM으로 출처가 표시됩니다. 위 예시들이 "LLM을 부르지 않는다"고 한 것은 그 오류가 규칙으로 해결되는 종류이기 때문입니다.
LLM을 부르는 경우

규칙에 없는 오류, 규칙 패치 후에도 같은 오류, 실행 파일 경로 문제처럼 맥락을 읽어야 하는 경우입니다.

바로 멈추는 경우

사전 점검 실패(결제·권한), 이미지 업로드 실패, 타임아웃, 함수 빌드 실패, 앱 코드 자체의 오류입니다. Dockerfile을 고쳐서는 해결되지 않으니 헛돌지 않고 사람에게 넘깁니다.

지키는 규칙

healer는 Dockerfile만 고칩니다. 앱 소스는 건드리지 않고, 소스 수정이 필요해 보이면 제안만 로그로 남깁니다. 재시도는 최대 3회입니다.

DATABASEDB 자동 프로비저닝

안내문의 "대충 만든 앱도 SQLite를 적절히 설정한 RDS로" 예시를 구현한 부분입니다. 서버리스 컨테이너는 재시작하면 디스크가 사라지고 인스턴스가 여러 개로 늘기도 해서, SQLite 파일에 저장하면 "배포는 성공했는데 데이터가 증발"합니다. 그래서 DB가 필요한 앱을 알아보고, 타깃에 맞는 진짜 DB를 만들어 연결해 줍니다.

1. 어떤 앱에 DB를 붙이나 (감지)

deployer가 소스 파일을 훑어 아래 중 하나라도 나오면 "Postgres가 필요한 앱"으로 판단합니다. analyzer도 같은 사실을 분석 카드에 "외부 저장소가 필요합니다: postgres"로 알려 줍니다.

DATABASE_URL 을 읽는 코드psycopg · asyncpg · pg8000sqlalchemyNode pg · prismapymysql · mysqlclient

설정으로 끌 수도 있고(DEPLOYER_DATABASE=), 감지와 상관없이 항상 붙일 수도 있습니다(postgres).

2. 타깃별로 무엇을 만드나

local

① 네트워크. cloudmorph라는 Docker 네트워크를 만듭니다. 같은 네트워크 안의 컨테이너끼리는 이름으로 서로를 찾습니다.

② DB 컨테이너. postgres:16-alpine을 <앱>-db라는 이름으로 띄우고, 데이터를 <앱>-dbdata 볼륨에 저장합니다. 이미 떠 있으면 재사용합니다.

③ 준비 확인. pg_isready가 성공할 때까지 기다립니다.

④ 주입. 앱 컨테이너에 아래 값을 넣고 같은 네트워크로 띄웁니다.

DATABASE_URL=postgresql://app:app@<앱>-db:5432/app
cloudrun

① 공유 인스턴스. Cloud SQL 인스턴스 cloudmorph-pg(PostgreSQL 16)는 미리 하나 만들어 두었습니다. 인스턴스 생성은 10분이 걸리지만 그 안에 DB를 추가하는 것은 1초입니다.

② 앱 전용 DB·계정. 앱 이름으로 데이터베이스와 사용자를 만들고, 비밀번호는 배포 때마다 새로 정합니다. 비밀번호는 실행 로그에 남기지 않습니다.

③ 연결. Cloud Run 배포 명령에 인스턴스 연결 옵션을 붙이면, 구글이 컨테이너 안에 유닉스 소켓을 열어 줍니다.

④ 주입.

DATABASE_URL=postgresql://<앱>:<비밀번호>@/<앱>
  ?host=/cloudsql/weighty-forest…:asia-northeast3:cloudmorph-pg
node

① 노드 선택 후 그 노드에 SSH로 들어가 local과 같은 방식으로 Postgres 사이드카를 띄웁니다.

② 주입. local과 같은 형식의 DATABASE_URL을 넣습니다.

③ stateful 표시. 이 앱은 자동 확장 대상에서 빠집니다. 복제본을 다른 노드에 만들면 그 노드에는 다른 DB가 생겨 데이터가 갈라지기 때문입니다. 감시 루프는 CPU가 높아도 "DB가 붙어 있어 복제하지 않음"으로 기록만 합니다.

function 타깃에는 DB를 붙이지 않습니다.

4. 비용과 보안

Cloud SQL은 가장 작은 사양(db-f1-micro)으로 월 1만~1만5천 원이며 모든 앱이 나눠 씁니다. 사이드카는 이미 있는 서버·VM 위에서 돌아 추가 비용이 없습니다. Cloud Run 쪽은 Cloud Run 서비스 계정에 Cloud SQL 접속 권한만 주었고, DB는 공인 인터넷이 아니라 구글 내부 소켓으로만 붙습니다.

일부러 하지 않은 것. SQLite 경로를 코드에 박아 둔 앱에는 DB를 붙이지 않습니다. 앱이 읽지도 않는 주소를 넣어 봐야 앱은 여전히 SQLite에 쓰므로 눈속임이기 때문입니다. 이런 앱은 analyzer가 "SQLite 파일이 재시작 때 사라진다"는 위험을 알려 주고, 서버리스 대신 node나 local을 권합니다. 앱이 DATABASE_URL을 읽도록 코드를 고치는 일은 사람의 몫으로 남겼습니다(healer는 소스를 고치지 않음).

NODE POOL노드 풀과 자동 확장

쿠버네티스처럼 중앙에서 컨테이너를 배치하되, 여러 회사의 VM을 하나의 풀로 다루는 구조입니다. 핵심은 "SSH와 Docker가 되는 기계"라는 추상화 하나로 GCP, 오라클, AWS, 내 PC를 모두 같은 코드로 다룬다는 점입니다.

노드 선택

모든 노드에 SSH로 한 번씩 들어가 1분 부하, CPU 수, 남은 메모리, 컨테이너 수를 읽습니다. 점수가 가장 낮은(한가한) 노드를 고릅니다.

score = load1 / cpus + 0.5 × 메모리압박 + 0.05 × 컨테이너수

노드에는 레지스트리 인증도 SSH 키도 두지 않습니다. 이미지는 서비스 쪽에서 흘려 넣습니다.

자동 확장 규칙

감시 루프가 복제본의 CPU를 cgroup 누적값 두 번의 차이로 재서 구간 평균을 냅니다. 50%를 2회 연속 넘으면 다른 노드에 복제하고 라우터(Caddy)에 업스트림을 추가합니다. 노드가 바닥나면 "확장 보류"로 기록합니다.

부하가 빠지고 최신 복제본이 2분 이상 살았으면 하나씩 줄입니다. 응답 헤더 X-Cloudmorph-Upstream에 어느 노드가 처리했는지 찍힙니다.

실측. 초당 약 1,000건 부하에서 CPU 94%를 감지해 20초 만에 두 번째 노드로 복제했고, 트래픽이 두 노드로 나뉘며 p95 지연 48ms를 유지했습니다.
노드회사사양상태
gcp-node-1, gcp-node-2Google Cloud (서울)e2-small, x86운영 중
aws-node-1AWS (서울, ap-northeast-2)t3.small, x86운영 중. 서버가 이 노드를 골라 배포하고, GCP 라우터가 AWS로 트래픽을 보내는 것까지 실측

새 회사의 VM을 붙이는 데 deployer 코드는 한 줄도 바꾸지 않았습니다. VM에 Docker를 깔고, 서버의 SSH 공개키를 등록하고, 노드 목록 파일에 한 줄을 추가했을 뿐입니다.
